## 🚩 阶段一：挑战

> **只看这个阶段，自己想 10 分钟。不要往下翻。**

### 场景：十亿条网址的爬虫去重

你在写一个网页爬虫，要去重——**已经抓过的网址不再抓**。网址总数有 **10 亿**条，每条平均 50 字节。

如果用普通的哈希集合（`set`）存全部网址：

```
10 亿条 × 50 字节 ≈ 50 GB 内存
```

太贵了。而且你其实**不需要 100% 精确**：

- 如果网址**抓过**，你**必须**说"抓过"（绝不能漏判，否则重复抓）
- 如果网址**没抓过**，你偶尔说"抓过"也没关系（少抓一次，可接受）

换句话说：**允许"假阳性"（把不在的说成在），但绝不允许"假阴性"（把在的说成不在）。**

### 要你回答

1. 设计一个结构，用**远小于 50 GB** 的空间（比如 1~2 GB）回答"这个网址是否**可能**抓过"。
2. 它要满足：**已在集合里的元素，查询一定返回"在"；不在的，只可能"误报"，不可能"漏报"。**
3. 提示：你只需要一个**位数组**和几个**哈希函数**。

> 💬 *先别急着翻。想想：一个哈希函数 + 一个位数组会发生什么？为什么需要多个哈希函数？"误报"是怎么产生的？*

> **给自己最后一次机会——先试再想 5 分钟。还是没思路？逐条看提示。**

**提示 1：从「一个哈希 + 一个位数组」开始**

不要存元素本身，只存**指纹**。开一个长度 `m` 的位数组，初始全 0。加入元素 `x` 时，算一个哈希 `h(x) % m`，把那个位置设为 1：

```
加入 x：  bits[h(x) % m] = 1
查询 x：  bits[h(x) % m] == 1 ?
```

**提示 2：一个哈希会撞车**

不同元素可能哈希到同一个位置——撞车。你**无法区分**"这个 1 是 x 自己写的，还是别的元素写的"。这就是误报的来源。

但反过来：如果 `bits[h(x)%m] == 0`，那 x **一定没被加过**（因为加入 x 时一定会把它置 1）。这就是"无假阴性"的来源。

**提示 3：用多个哈希降低误报**

一个哈希容易误报。那就用 **k 个独立的哈希函数**，加入时把 k 个位置都置 1：

```
加入 x：  bits[h1(x)%m] = bits[h2(x)%m] = ... = bits[hk(x)%m] = 1
查询 x：  这 k 个位置全是 1 吗？
```

- k 个位置**全是 1** → 可能在（可能被别的元素凑巧全填上了）
- 任意一个位置是 **0** → **一定不在**（因为 x 若被加过，这 k 个位置必然全 1）

**提示 4：误报率怎么估算？**

若已加入 `n` 个元素，位数组长度 `m`，用了 `k` 个哈希，那么某个位仍为 0 的概率 ≈ `e^(-kn/m)`，误报率 ≈ `(1 - e^(-kn/m))^k`。给定目标误报率，可以反过来选最优的 `k` 和 `m`。

### 核心洞察

> **布隆过滤器 = 用「多个哈希 + 一个位数组」，把精确集合压缩成概率集合。**
>
> 牺牲一点正确率（假阳性），换取**空间和速度的数量级提升**。

三个要点：

**① 只存指纹，不存元素**——空间从 O(元素字节数) 降到 O(位数)。

**② 天然"无假阴性"**——已加入的元素，它的所有哈希位必然都是 1，查询永远返回"在"。

**③ 误报可控**——误报率随位数组变大、哈希变多而指数下降，可按需调节。

```
查询结果：
  任意一个哈希位 = 0   →  一定不在  ✓ 绝对可靠
  所有哈希位 = 1       →  可能在    （可能误报）
```

### 三步翻译——自己写代码

**第一步：说清意图**

```
写一个 BloomFilter：
- __init__(size, num_hashes)：位数组 + 哈希个数
- add(item)：把 item 的 num_hashes 个哈希位都置 1
- contains(item)：所有哈希位都是 1 才返回 True
```

**第二步：拆成标准操作**

```
→ 生成 k 个哈希位置：对 item 用 k 个不同的"盐"分别哈希
→ add：遍历位置，bits[pos] = 1
→ contains：遍历位置，只要有一个是 0 就返回 False
→ 全 1 才返回 True
```

**第三步：匹配到代码**

| 标准操作 | 代码实现 |
|---------|---------|
| 位数组 | `self.bits = [0] * size` |
| k 个哈希位置 | `int(hashlib.md5(f"{i}:{item}".encode()).hexdigest(), 16) % size` |
| 加入 | `self.bits[pos] = 1` |
| 查询 | `all(self.bits[pos] == 1 for pos in positions)` |


### 参考实现

```python
import hashlib


class BloomFilter:
    """用多个哈希 + 位数组实现。空间小，允许假阳性，绝不假阴性。"""

    def __init__(self, size: int = 1000, num_hashes: int = 3):
        self.size = size
        self.num_hashes = num_hashes
        self.bits = [0] * size

    def _positions(self, item):
        """为 item 生成 num_hashes 个（伪）独立的位位置。"""
        out = []
        for i in range(self.num_hashes):
            # 加"盐"让每个哈希不同；md5 结果确定、可复现
            digest = hashlib.md5(f"{i}:{item}".encode("utf-8")).hexdigest()
            out.append(int(digest, 16) % self.size)
        return out

    def add(self, item):
        for pos in self._positions(item):
            self.bits[pos] = 1

    def contains(self, item) -> bool:
        return all(self.bits[pos] == 1 for pos in self._positions(item))
```

### 深度思考——为什么"可能不在"如此有用？

直觉上，"答案含糊"听起来是缺点。但在很多场景里，**"一定不在"比"一定在"更有价值**：

- 爬虫：对**没抓过的**网址，布隆说"不在"→ 放心抓；说"可能在"→ 那就当它抓过了（少抓一次无害）
- 缓存穿透：先问布隆"这个 key 可能存在吗？"→ 不在就直接返回空，**挡住海量不存在的 key 打到数据库**
- 密码泄露检测：问"这个密码是否在泄露库里？"→ 不在就是安全的，在再去做精确核对

### 这个模式还出现在……

| 领域 | 问题 | 对应关系 |
|------|------|---------|
| **爬虫去重** | 判断网址是否已抓过 | 允许误报，绝不漏报 |
| **缓存穿透防护** | 挡掉不存在的 key 的恶意查询 | 先布隆过滤，再查数据库 |
| **密码泄露检测** | 检查密码是否在泄露库中 | 隐私友好：只存指纹不存明文 |
| **数据库 / LSM-Tree** | 判断 key 是否可能在某层 SSTable | 减少磁盘查找 |
| **区块链 SPV 钱包** | 判断交易是否可能在某区块 | 轻节点用布隆请求相关交易 |
| **垃圾邮件过滤** | 快速判断地址是否在黑名单 | 允许少量误判 |
